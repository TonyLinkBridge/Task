# 第 23 项：详细执行计划（白话版）

## 最终目标

建立一套安全的自动测试，让电脑能够用一名员工和两位管理员的身份，完整走完任务、内容、审核、文件和发布流程。

测试只能使用专用练习环境，不能碰正式资料，也不能发送 Slack 消息。

## 现在的状态

- 测试做法：已经决定；
- 详细步骤：已经规划；
- 专用测试环境：还没建立；
- 自动测试：还没开始写；
- 第 23 项：仍然是“未完成”。

## 执行时怎样汇报

下面共有八个阶段。每完成一个阶段，我都会用白话告诉你：

1. 这次完成了什么；
2. 现在系统可以做什么；
3. 我实际测试了什么；
4. 下一步是什么。

## 第一阶段：先装上安全锁

### 要做什么

先建立一个检查程序。每次运行已登录自动测试前，它都会确认目前连接的是练习环境。

### 必须检查

- Clerk 是测试版本；
- Supabase 不是正式项目 `opjhumwfvasvgzmsiyhu`；
- 网站在本机运行；
- 没有 Slack Bot Token；
- 这是明确标记过的专用测试环境；
- 所有必要资料都已经填写。

### 如果检查失败

测试立即停止，不会登录、建立任务、上传文件或修改数据库。

错误信息会直接说明缺了什么，或哪一个服务误连到正式环境。

### 会新增什么

- 一份没有真实密码的测试环境示范文件；
- 一套测试环境检查；
- 暂时登录资料和测试运行资料的忽略规则；
- 一个可以手动确认“练习环境安全”的指令。

### 怎样算完成

我们会故意放入以下错误资料来测试安全锁：

- 正式 Clerk 密钥；
- 正式 Supabase 地址；
- 正式网站地址；
- Slack Bot Token。

四种情况都必须被拦住；正确的练习环境则必须通过。

## 第二阶段：建立完全分开的练习环境

### Clerk

建立或使用一个 Clerk Development 环境，取得测试用的登录资料。

正式版本的密钥不能在这里使用。

### Supabase

建立一个叫作 `Task E2E` 的新项目。

把目前程序使用的 11 份数据库设置全部放进去，让测试数据库的结构和正式数据库相同。

完成后确认：

- 任务和内容相关资料表存在；
- 审核和历史资料表存在；
- 私人文件空间 `content-files` 存在；
- Slack 通知频道是空白；
- Slack 发送记录是 0 条。

### Liveblocks

建立一个叫作 `Task E2E` 的新项目，用来保存测试正文和指定文字留言。

### 本机设置

把三个测试服务的资料放进电脑的 `.env.e2e.local`。

这个文件不会上传 GitHub。

### 怎样算完成

运行安全检查后，只显示：

`dedicated environment ready`

它不能在画面上显示任何密码或密钥。

## 第三阶段：准备一名员工和两位管理员

### 固定测试账号

- `E2E Employee`：员工；
- `E2E Admin A`：管理员；
- `E2E Admin B`：管理员。

### 自动准备方式

每次开始测试时，系统会：

1. 找出这三个账号；
2. 账号不存在就自动建立；
3. 把员工账号设成员工；
4. 把另外两个账号设成管理员；
5. 写入指定的 Slack Workspace 身份；
6. 让三个账号各登录一次；
7. 分别保存三个暂时登录状态；
8. 确认 Supabase 里的角色也正确。

然后系统会建立或恢复 `E2E 测试平台`，并再次把 Slack 频道清空。

指定的 Workspace 编号是 `T094DTFCVA8`，三个账号都必须使用同一个编号。

### 密码怎样保存

三个测试账号可以共用一个专用测试密码。

密码只放在：

- 电脑的测试环境文件；
- GitHub 的 Secrets 保险箱。

密码不会写进代码，也不会上传到 GitHub。

### 怎样算完成

- 员工账号自动进入任务页面；
- 两位管理员都能自动进入任务页面；
- 三个登录状态不会混在一起；
- 数据库显示一名员工和两名管理员；
- 发布平台列表里有 `E2E 测试平台`。

## 第四阶段：建立自动测试的运行和清理机制

### 每次测试都有自己的编号

每次运行会产生一个编号，例如：

`e2e-20260829-001122-a1b2c3`

这次建立的任务、内容、文件和正文房间都会记录在一份临时清单里。

### 测试分类

自动测试会分成四组：

1. 未登录检查；
2. 准备三个登录身份；
3. 已登录完整流程；
4. 测试结束后的清理。

已登录测试一次只运行一组，避免两个流程同时修改同一条内容。

### 清理顺序

测试结束后会依次清理：

1. 上传的 PDF；
2. Slack 测试记录和系统历史；
3. 指定文字留言；
4. 审核记录和批准记录；
5. 内容和任务之间的连接；
6. 普通任务、发布任务和任务留言；
7. 测试内容和正文版本；
8. Liveblocks 测试房间；
9. 电脑里的暂时登录状态。

### 防止误删

系统会在删除前检查标题。

只有标题带着本次测试编号，才允许删除。正常任务或正式内容不会被清理器删除。

### 怎样算完成

- 测试成功时能清理干净；
- 测试中途失败时也会清理；
- 如果还有残留，测试会失败并列出残留资料；
- 清理器遇到普通标题时会拒绝删除。

## 第五阶段：检查员工和管理员权限

### 先修正一个已知问题

现在员工直接进入管理员页面时，拒绝页面可能错误显示成 Slack Workspace 不符合。

要把它改成：

- 标题：`需要管理员权限`；
- 说明：`这个页面只开放给管理员。`

真正的 Workspace 错误仍然保留原本提示。

### 浏览器会实际检查

使用员工账号：

- 看得到任务；
- 看得到内容排期；
- 看不到管理员设置；
- 看不到历史记录；
- 直接打开管理员网址会被正确拒绝。

使用管理员 A：

- 能打开管理员设置；
- 能看到发布平台；
- 能打开系统历史。

### 怎样算完成

员工和管理员的所有检查都通过，而且页面不再显示错误的拒绝原因。

## 第六阶段：检查普通任务完整流程

### 电脑会做什么

员工账号会：

1. 打开任务页面；
2. 按“新增任务”；
3. 填写测试标题和说明；
4. 选择 `E2E Employee`；
5. 选择“紧急”；
6. 填写完成时间；
7. 按“保存任务”；
8. 把任务拖到“正在做”；
9. 打开任务并留言；
10. 把任务拖到“已经完成”；
11. 重新载入页面。

### 要确认什么

- 任务真的建立成功；
- 拖动后状态真的改变；
- 留言真的保存；
- 重新载入后任务仍在“已经完成”；
- 重新载入后留言仍然存在。

### 怎样算完成

整个流程一次通过，并且结束后测试任务和留言都被清理。

## 第七阶段：检查内容、文件、审核和发布

这是第 23 项最重要的一段。

### A. 员工建立内容

员工会：

1. 打开建立内容页面；
2. 输入带测试编号的标题；
3. 选择 `E2E 测试平台`；
4. 选择自己为负责人；
5. 把发布时间设成已经到达；
6. 按“建立内容”。

系统必须同时建立一条发布任务。

发布任务必须显示：`由内容排期控制，不能手动拖动`。

### B. 正文和文件

员工会：

1. 在 BlockNote 输入测试正文；
2. 等待“已经同步”；
3. 上传一个小型 PDF；
4. 把同一个 PDF 下载回来；
5. 比较两个文件是否完全相同。

### C. 员工送审

员工按“交给上司检查”后，必须出现：

- 状态是“等待审核”；
- 正文不能修改；
- 上传按钮消失；
- 批准人数是 `0/2`；
- 指定文字留言仍然可以使用。

员工会实际新增一条指定文字留言，不能只检查按钮有没有出现。

### D. 第一轮审核

1. 管理员 A 批准；
2. 页面显示还在等待另一位管理员；
3. 管理员 B 写下修改原因；
4. 管理员 B 按“要求修改”；
5. 内容回到“需要修改”。

### E. 修改和重新提交

1. 员工修改正文；
2. 等待“已经同步”；
3. 员工重新提交；
4. 系统确认旧批准已经失效；
5. 批准人数重新计算。

### F. 两位管理员批准新版

1. 管理员 A 批准新版；
2. 内容仍然不能直接通过；
3. 管理员 B 批准新版；
4. 内容进入“已经批准”或“等待发布”。

### G. 确认发布

负责人按“确认已经发布”后，必须确认：

- 内容变成“已经发布”；
- 发布任务自动进入“已经完成”；
- 内容页面有完整审核记录；
- 管理员历史有完整操作记录；
- 操作人和时间正确；
- Slack 发送记录仍然是 0 条。

### 怎样算完成

上面 A 到 G 全部通过，而且测试 PDF、内容、任务、审核记录、留言和正文房间都清理干净。

## 第八阶段：完整验收和 GitHub 自动运行

### 本机完整检查

会依次检查：

- 所有程序测试；
- 所有页面和功能检查；
- 正式打包；
- 未登录浏览器测试；
- 三个账号的已登录浏览器测试；
- 测试资料清理结果。

任何一项失败，第 23 项都不能改成完成。

### GitHub 自动测试

GitHub 会准备同一套专用测试资料，但密码和密钥只放在 GitHub Secrets。

GitHub 不会获得：

- 正式 Clerk 密钥；
- 正式 Supabase 密钥；
- 正式 Liveblocks 密钥；
- Slack Bot Token。

同一时间只允许一套测试运行。

测试失败时，GitHub 会保存截图和测试过程七天，方便检查。

### 最后更新任务表

只有以下事情全部完成，才会把任务表第 23 项改成“完成”：

- 本机所有检查通过；
- GitHub 自动测试成功一次；
- Slack 发送记录是 0；
- 没有测试资料残留。

## 执行过程中会动到哪些地方

| 地方 | 白话说明 |
|---|---|
| 测试环境设置 | 保存练习环境的地址和密钥名称，不保存真实值 |
| 自动测试设置 | 安排未登录测试、三个登录身份和清理步骤 |
| Clerk 测试准备 | 建立一名员工和两位管理员的测试身份 |
| Supabase 测试准备 | 检查账号、平台、频道和测试资料 |
| 任务自动测试 | 检查建立、留言、拖动和保存 |
| 内容自动测试 | 检查正文、PDF、审核、修改、批准和发布 |
| 权限页面 | 修正员工被拒绝时显示的原因 |
| GitHub 自动测试 | 在专用环境重新跑完整检查 |
| 任务表 | 全部通过后才把第 23 项改成完成 |

## 遇到问题时怎样处理

- 缺少测试资料：停止，并列出缺少的名称；
- 误连正式环境：立即停止，不做任何修改；
- 某个账号登录失败：说明是哪一个账号；
- 页面等太久：保存截图和操作过程；
- PDF 下载后不相同：保留证据并执行清理；
- 清理失败：列出没有清掉的资料；
- GitHub 失败：保留测试报告七天。

## 不会顺便做的事情

为了避免范围越来越大，第 23 项不会顺便处理：

- 真实 Slack 登录测试；
- 向真实 Slack 频道发送测试消息；
- 两个人同时即时编辑正文；
- 真正的月历；
- 其他任务表项目。

这些内容会继续按照原本的任务编号分别处理。
