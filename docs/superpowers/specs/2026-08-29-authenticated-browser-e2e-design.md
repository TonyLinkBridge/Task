# 第 23 项：登录后的完整浏览器自动测试设计（白话版）

## 这项要完成什么

我们要建立一套自动测试，让电脑像真人一样打开网站、登录账号、按按钮、填写内容、上传文件和拖动任务。

它会检查这些重要流程：

- 员工能不能正常使用任务和内容排期；
- 员工能不能进入管理员页面；
- 普通任务能不能建立、留言、拖动和完成；
- 排期内容能不能写正文、上传文件和提交检查；
- 是否真的需要两位不同管理员批准；
- 管理员要求修改后，员工能不能修改并重新提交；
- 到了发布时间后，员工能不能确认已经发布；
- 发布后，对应任务和历史记录有没有一起更新；
- 整个测试过程有没有错误发送 Slack 消息。

## 为什么不能直接拿正式网站测试

这套测试会真正建立任务、上传文件和改变审核状态。如果直接使用正式资料，可能会：

- 留下一堆测试任务和测试内容；
- 把测试提醒发到正式 Slack 频道；
- 不小心改到员工正在使用的资料；
- 测试失败后留下难以清理的文件。

所以我们会建立一个完全分开的“测试练习场”。

这个练习场包括：

- 一个专门测试用的 Clerk 登录环境；
- 一个独立的 Supabase 数据库；
- 一个独立的 Liveblocks 正文和留言环境；
- 在电脑上运行的网站；
- 完全不连接 Slack Bot，也不选择任何 Slack 频道。

## 测试会使用哪三个人

测试环境会固定保留三个测试账号：

1. `E2E Employee`：员工；
2. `E2E Admin A`：第一位管理员；
3. `E2E Admin B`：第二位管理员。

三个账号都会被标记为属于指定的 Slack Workspace：`T094DTFCVA8`。

这些账号只是测试替身，不是真实员工账号。登录密码只会放在电脑和 GitHub 的保险箱里，不会上传到程序代码。

## 防止误碰正式资料的安全锁

每次开始测试前，系统必须先检查：

- Clerk 必须是测试版本，不能是正式版本；
- Supabase 不能是正式项目 `opjhumwfvasvgzmsiyhu`；
- Liveblocks 必须是另外建立的测试项目；
- Slack Bot Token 必须不存在；
- Slack 通知频道必须保持空白；
- 网站只能使用电脑上的 `http://127.0.0.1:3000`；
- 必须明确写着这是专用测试环境。

只要有一项不符合，测试会马上停止，而且不会建立或修改任何资料。

错误提示会直接说明是哪一个地方不安全，例如：

- “目前连接的是正式 Clerk，测试已经停止”；
- “目前连接的是正式 Supabase，测试已经停止”；
- “测试环境发现 Slack Bot Token，测试已经停止”。

## 开始测试前会准备什么

自动测试开始前会完成以下准备：

1. 确认三个测试账号都存在；
2. 把一个账号设成员工，另外两个设成管理员；
3. 让三个账号各登录一次；
4. 确认数据库里也出现了这三个账号；
5. 建立一个叫作 `E2E 测试平台` 的发布平台；
6. 再次确认 Slack 频道是空白；
7. 为这一次测试产生一个独一无二的编号。

测试编号会类似：`e2e-20260829-001122-a1b2c3`。

这次建立的任务和内容都会带着这个编号，方便找到和清理。

## 自动测试会怎样进行

### 第一部分：检查员工和管理员权限

电脑会使用员工账号登录，然后检查：

- 可以打开任务页面；
- 可以打开内容排期；
- 左边没有管理员菜单；
- 直接输入管理员设置网址也会被拒绝；
- 直接输入历史记录网址也会被拒绝；
- 拒绝页面显示“需要管理员权限”，不会错误显示成 Slack Workspace 不符合。

接着电脑会使用管理员账号登录，确认管理员设置和历史记录都能正常打开。

### 第二部分：检查普通任务

员工会自动完成以下动作：

1. 建立一条测试任务；
2. 填写标题、说明、负责人、优先级和完成时间；
3. 把任务从“还没开始”拖到“正在做”；
4. 打开任务并写一条留言；
5. 回到看板，把任务拖到“已经完成”；
6. 重新打开页面；
7. 确认任务仍在“已经完成”，留言也还在。

这部分会使用真实鼠标移动方式拖动，不是假装修改数据库状态。

### 第三部分：建立排期内容

员工会自动完成以下动作：

1. 建立一条测试内容；
2. 选择 `E2E 测试平台`；
3. 选择 `E2E Employee` 为负责人；
4. 把发布时间设成已经到达；
5. 确认系统自动建立一条发布任务；
6. 确认发布任务显示“由内容排期控制，不能手动拖动”；
7. 在 BlockNote 输入测试正文；
8. 等到正文显示“已经同步”；
9. 上传一个很小的测试 PDF；
10. 再把 PDF 下载回来；
11. 比较上传前和下载后的文件，确认没有损坏。

### 第四部分：检查送审后的正文和留言

员工按“交给上司检查”后，系统会检查：

- 状态变成“等待审核”；
- 正文不能继续修改；
- 上传按钮消失；
- 批准人数显示 `0/2`；
- 员工仍然可以针对指定文字留言；
- 新留言可以在“指定文字留言”区域看到。

### 第五部分：检查两位管理员审核

流程会按照真实使用方式进行：

1. 管理员 A 批准第一票；
2. 内容不能因为第一票就直接通过；
3. 管理员 B 留下修改说明并按“要求修改”；
4. 员工看到“需要修改”；
5. 员工修改正文并重新提交；
6. 旧的批准不能继续计算；
7. 管理员 A 再次批准新版；
8. 管理员 B 批准第二票；
9. 只有第二票完成后，内容才算批准完成。

### 第六部分：检查发布

由于测试内容的发布时间已经到达，负责人会按“确认已经发布”。

系统必须同时出现这些结果：

- 内容状态变成“已经发布”；
- 对应发布任务自动进入“已经完成”；
- 内容页面记录是谁发布和什么时候发布；
- 管理员历史也有发布记录；
- 整个过程中没有建立任何 Slack 发送记录。

### 第七部分：检查历史记录

测试会检查内容页面和管理员历史，确认能找到：

- 第一次提交检查；
- 管理员 A 的第一次批准；
- 管理员 B 要求修改；
- 员工重新提交；
- 管理员 A 批准新版；
- 管理员 B 批准新版；
- 员工确认已经发布。

每一项都必须有操作人和时间。

## 测试完成后怎样清理

无论测试成功还是失败，系统都会尝试清理这次建立的资料。

清理内容包括：

- 测试上传的 PDF；
- 测试内容和正文版本；
- 审核记录和批准记录；
- 指定文字留言；
- 普通任务、发布任务和任务留言；
- 这次测试使用的 Liveblocks 房间；
- 电脑里暂时保存的登录状态。

系统只允许删除带着本次测试编号的资料。如果发现标题不是测试标题，会拒绝删除，避免误删正常资料。

三个固定测试账号和 `E2E 测试平台` 会保留，方便下次继续使用。

清理完成后，系统会再检查一次。如果仍有残留，这次测试会被判定为失败，并列出没清掉的资料。

## GitHub 会怎样自动测试

本机测试稳定后，GitHub 也会运行同一套检查。

GitHub 会：

1. 准备程序和浏览器；
2. 更新专用测试数据库；
3. 在 GitHub 的电脑上启动网站；
4. 运行未登录和已登录测试；
5. 无论成功或失败都执行清理；
6. 测试失败时保留截图和过程记录七天。

GitHub 同一时间只允许运行一套会写入资料的测试，避免两次测试互相影响。

## 什么情况才算第 23 项完成

以下项目必须全部通过：

- 未登录保护测试通过；
- 三个测试账号都能自动登录；
- 员工和管理员权限正确；
- 普通任务完整流程通过；
- 内容正文和同步通过；
- PDF 上传和下载通过；
- 两位管理员审核流程通过；
- 发布和发布任务联动通过；
- 内容历史和管理员历史正确；
- Slack 发送记录保持为零；
- 测试资料全部清理干净；
- 程序测试、代码检查和正式打包全部通过；
- GitHub 自动测试成功运行一次。

只有全部完成后，任务表第 23 项才会改成“完成”。

## 这一次不会处理什么

以下项目不属于第 23 项：

- 不测试真实 Slack 注册；
- 不向任何真实 Slack 频道发送消息；
- 不使用正式账号和正式资料；
- 不测试两个人同时即时编辑正文。

最后一项仍然属于任务表第 7 项，目前继续保持“暂时跳过”。
