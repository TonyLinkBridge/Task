# 已登录浏览器自动测试设计

## 目标

为内部工作台建立一套可以重复运行的已登录浏览器测试，真实覆盖任务、内容排期、正文、文件、审核、发布和管理员权限。测试只连接专用测试环境，不读取或修改正式环境资料，也不向正式 Slack 频道发送消息。

## 为什么需要专用测试环境

目前的 Playwright 测试只确认未登录用户会被带回登录页。完整流程会建立任务、上传文件、改变审核状态并确认发布，如果直接连接正式环境，会留下测试资料，也可能触发 Slack 通知。

专用测试环境包含：

- Clerk Development 实例；
- 独立 Supabase 测试项目；
- 独立 Liveblocks 测试项目；
- 本机运行的 Next.js 网站；
- 不设置 Slack Bot Token，并把通知频道留空。

## 测试身份

Clerk Development 实例固定建立三个测试账号：

- `employee+clerk_test@linkbridge.test`：员工；
- `admin-a+clerk_test@linkbridge.test`：管理员 A；
- `admin-b+clerk_test@linkbridge.test`：管理员 B。

三个账号都在 Clerk public metadata 保存专用测试 Workspace 身份：

```json
{
  "role": "employee 或 admin",
  "slackTeamId": "T094DTFCVA8",
  "slackVerifiedAt": "固定测试时间"
}
```

测试使用 Clerk 官方的 `@clerk/testing/playwright`。全局准备程序通过邮箱为三个账号建立登录状态，并分别保存为员工、管理员 A、管理员 B 的 Playwright `storageState`。登录状态文件只存在本机或 CI 临时目录，并加入 `.gitignore`。

## 防止误连正式环境

开始任何已登录写入测试前，准备程序必须检查：

- Clerk Publishable Key 必须以 `pk_test_` 开头；
- Supabase URL 不能包含正式项目编号 `opjhumwfvasvgzmsiyhu`；
- Supabase 测试项目必须没有 Slack 频道；
- `SLACK_BOT_TOKEN` 在测试环境必须为空；
- `E2E_TEST_ENVIRONMENT=dedicated` 必须存在；
- 网站地址默认只能是 `http://127.0.0.1:3000`。

任何一项不符合，测试立即停止，并用白话说明是哪一个安全条件不正确。

## 测试环境准备

测试环境使用仓库现有的 11 份 Supabase migration 建立相同结构，包括私人文件 bucket。全局准备程序负责：

1. 确认三个 Clerk 测试账号存在，并写入正确 metadata；
2. 打开本机网站，让三个账号各登录一次，使 profile 同步到 Supabase；
3. 确认三个 profile 的角色分别是员工、管理员、管理员；
4. 确认通知频道为空；
5. 建立一个名为 `E2E 测试平台` 的发布平台；
6. 产生本次运行的唯一编号，例如 `e2e-20260829-001122`。

所有测试资料的标题都带本次运行编号，方便识别和清理。

## Playwright 结构

保留现有匿名测试，并增加以下项目：

- `anonymous`：现有未登录保护测试；
- `auth-setup`：准备三个登录状态；
- `authenticated`：依次运行完整流程，使用一个 worker，避免多人流程互相抢状态。

已登录流程共用一个运行资料文件，只保存本次测试建立的任务编号、内容编号和附件路径。这个文件同样放在被忽略的临时目录。

## 自动测试流程

### 1. 员工权限

- 员工登录后可以打开任务和内容排期；
- 左边菜单没有管理员入口；
- 直接打开管理员设置和历史页面会进入正确的“没有管理员权限”页面；
- 页面不能误报 Slack Workspace 不符合。

### 2. 普通任务

- 员工建立一条带运行编号的普通任务；
- 填写负责人、优先级和到期时间；
- 打开任务详情并留言；
- 从“还没开始”拖到“进行中”，再拖到“已经完成”；
- 重新打开页面后，状态和留言仍然存在。

### 3. 建立排期内容

- 员工建立一条带运行编号的排期内容；
- 选择 `E2E 测试平台`、负责人和已到达的发布时间；
- 确认系统同时建立不能手动拖动的发布任务；
- 在 BlockNote 正文输入测试文字并确认同步完成；
- 上传一个很小的 PDF 测试文件；
- 下载文件并确认内容与上传前相同。

### 4. 两位管理员审核

- 员工提交审核后，正文锁定但留言仍可使用；
- 管理员 A 批准第一票，内容仍是等待审核；
- 管理员 B 退回并留言；
- 员工修改正文并重新提交；
- 管理员 A 和管理员 B 分别批准；
- 内容只有在第二票后进入“已经批准”；
- 历史记录显示首次送审、第一票、退回、重新送审和两票批准的人员及时间。

### 5. 确认发布

- 发布时间已经到达后，负责人可以按“已经发布”；
- 内容进入“已经发布”；
- 对应发布任务自动进入“已经完成”；
- 内容历史和管理员历史都显示发布人及时间。

### 6. 管理员功能

- 管理员可以打开平台设置、通知设置和历史页面；
- 历史页面能找到本次运行的建立、修改、送审、批准、退回、重新送审和发布记录；
- 通知频道保持为空，测试期间没有 Slack delivery 被建立。

## 测试文件

仓库增加一个固定的单页小型 PDF，页面只包含本次测试说明。测试下载后比较文件摘要，不依赖浏览器预览。

## 清理方式

全局清理程序只操作带本次运行编号的测试资料：

- 删除测试附件对象；
- 删除测试内容产生的版本、批准、留言、附件资料、历史和发布任务；
- 删除普通测试任务和留言；
- 保留三个固定测试账号和 `E2E 测试平台`，供下次使用；
- 删除本机临时登录状态和运行资料文件。

如果测试中途失败，清理程序仍然运行。清理失败会令整套测试失败，并列出没有清掉的测试资料，不会静默忽略。

## 环境变量

仓库只提供没有真实值的 `.env.e2e.example`。需要的值包括：

- Clerk Development Publishable Key 和 Secret Key；
- Clerk Development 三个测试账号共用的测试密码；
- 三个测试账号邮箱；
- Supabase 测试项目 URL、Publishable Key、Service Role Key 和数据库连接地址；
- Liveblocks 测试项目 Public Key 和 Secret Key；
- `E2E_TEST_ENVIRONMENT=dedicated`。

真实值只放在本机 `.env.e2e.local` 或 GitHub Actions Secrets。

## GitHub Actions

增加独立工作流程：

1. 安装依赖和 Chromium；
2. 把 migration 更新到 Supabase 测试项目；
3. 启动本机 Next.js；
4. 运行匿名和已登录浏览器测试；
5. 无论成功或失败都执行清理；
6. 失败时保存 Playwright trace 和截图，保留七天。

工作流程不会部署网站，也不会读取正式 Vercel、正式 Clerk、正式 Supabase 或 Slack secrets。

## 错误处理

- 缺少环境变量：在启动前停止并列出缺少的名称；
- 误连正式环境：立即停止，不执行任何写入；
- Clerk 登录失败：指出失败的测试身份；
- 页面状态超时：保存 trace 和截图；
- 上传或下载不一致：保留测试证据，然后执行清理；
- 清理失败：测试标记失败并列出残留标题。

## 完成标准

第 23 项只有在以下条件全部满足时才改为“完成”：

- 匿名测试通过；
- 三个测试身份自动登录成功；
- 任务、内容、审核、文件、发布和管理员限制全部通过；
- Slack delivery 数量保持为零；
- 清理后没有本次运行的任务、内容或附件残留；
- `pnpm test`、`pnpm lint`、`pnpm build` 和已登录 Playwright 测试全部通过；
- GitHub Actions 使用专用测试环境成功运行一次。

## 不在这项范围内

- 不测试真实 Slack OAuth 注册；
- 不向任何真实 Slack 频道发送消息；
- 不使用正式账号或正式资料；
- 不做两台浏览器同时即时编辑；该项目仍归第 7 项处理。
